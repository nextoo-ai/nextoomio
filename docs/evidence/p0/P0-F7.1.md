## Procedure

1. **Bench hardware documentation and inventory record (AC1):**
   - Implemented `docs/bench/record.md`: the official bench record form documenting the reference hardware inventory across all seven required components with models, revisions, electrical specifications, and wiring topology (Raspberry Pi 4 Model B, HiFiBerry Amp+, passive test speaker, MicroSD card with A/B partition layout from [ARCHITECTURE.md](../../../ARCHITECTURE.md) section 3.6, dedicated DC bench power supply, wired Gigabit Ethernet `eth0`, and switched AC power outlet) in accordance with [SPECIFICATION.md](../../../SPECIFICATION.md) section 2.1, [ROADMAP.md](../../../ROADMAP.md) section 2.1, [ARCHITECTURE.md](../../../ARCHITECTURE.md) section 4.1, and acceptance criterion AC1.
   - In accordance with the Architect's instructions for issue #31, all fields required by AC1 are provided in `docs/bench/record.md` as a form and marked `not yet recorded` until populated from physical hardware assembly readings.
   - Implemented `docs/bench/README.md`: test bench guide describing bench documentation, configuration setup, and remote power tool usage.

2. **Workstation power control tool and shell wrapper (AC2, AC3):**
   - Implemented `scripts/bench/power.py` using Python 3 standard library (`urllib.request`, `json`, `argparse`, `sys`, `time`).
   - Implemented POSIX `/bin/sh` wrapper `scripts/bench/power.sh` forwarding arguments to `power.py`.
   - Supported actions: `on`, `off`, `cycle` (off $\rightarrow$ delay $\rightarrow$ on), and `status`.
   - Enforced credential and URL sanitization in all logs, text output, and JSON reports: passwords (including those containing `@`), whole URL query strings (e.g. `?apikey=...` or arbitrary parameter names), Authorization headers (Bearer / Basic), and sensitive response bodies in HTTP error reports are redacted (CQ-R6).
   - Designed distinct exit codes: `0` (success), `1` (config/argument error), `2` (network unreachable/timeout), `3` (HTTP error status from outlet), `4` (action failed).

3. **Untracked local configuration and outlet interchangeability (AC3):**
   - Created `scripts/bench/outlet.example.json` shipping configuration templates for generic HTTP/REST, Shelly Gen 1 / Gen 2, Tasmota, Home Assistant REST (`home_assistant_rest`), and Mock drivers with placeholder values and no committed secrets or private IPs.
   - Updated `.gitignore` to ignore `/scripts/bench/outlet.json`, `/scripts/bench/*.local.json`, and `/.outlet.json`.
   - Supported configuration precedence: `--config <path>`, `NEXTOOMIO_OUTLET_CONFIG`, `scripts/bench/outlet.json`, `/.outlet.json`, `~/.config/nextoomio/outlet.json`.
   - Enabled switching between different outlet models solely by modifying the local configuration file without modifying source code.

4. **Automated test suite and CI verification:**
   - Implemented `scripts/test_bench_power.py` with 8 automated unit and fixture tests:
     - `test_missing_config_fails_cleanly`: verifies exit code `1` and guidance towards `outlet.example.json` when config is absent.
     - `test_mock_driver_operations`: verifies `on`, `off`, `cycle`, and `status` actions, delay timing, and failure modes.
     - `test_http_driver_mocked_requests`: verifies URL construction, HTTP methods, headers, and Bearer token transmission.
     - `test_shelly_and_tasmota_driver_configurations_ac3`: verifies driver adaptation for Shelly Gen 1, Shelly Gen 2 (RPC POST), Tasmota, and Home Assistant REST template.
     - `test_credential_redaction_cq_r6`: asserts that passwords containing `@`, whole URL query strings (including unlisted parameter names like `apikey`), Authorization headers, and sensitive HTTP error/mismatch bodies are redacted and never leaked in logs, stderr, or JSON reports.
     - `test_http_and_network_error_exit_codes`: verifies distinct exit code `3` for HTTP 500 errors and exit code `2` for network connection failures.
     - `test_power_sh_shell_wrapper`: verifies `/bin/sh scripts/bench/power.sh` execution.
     - `test_outlet_example_json_is_valid_and_safe`: asserts valid JSON and absence of private IP addresses or committed keys.

5. **Executed checks:**
   - Ran `make check` including `check-docs`, `check-doc-versions`, `check-evidence`, `check-i18n`, and `yocto-validate`.
   - Executed simulated power cycle transcript via `scripts/bench/power.sh --mock cycle --delay 1.0`.

## Missed targets

In accordance with the project owner's decision of 2026-11-15 and the Architect's instructions for issue #31, all Phase 0 software is implemented and statically/mock verified first in author sessions, while physical hardware measurements run on the assembled bench device afterwards. The following items require physical bench hardware:

- **AC2:** Physical confirmation of the bench device losing and regaining electrical power upon invocation of `scripts/bench/power.sh` against the physical switched outlet.
- **AC4:** Physical verification that following an idle power cycle, the Raspberry Pi 4 boots successfully from the microSD card and becomes reachable over OpenSSH on wired Ethernet without manual on-site intervention.
