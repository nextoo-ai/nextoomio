## Procedure

1. **SWUpdate update file type and packaging class (AC1, AC2, AC3, D-008):**
   - Created `meta-nextoomio/classes/image_types_nextoomio.bbclass` inheriting `image_types` to define image type `swu` with dependency `IMAGE_TYPEDEP:swu = "ext4.gz"`.
   - In `IMAGE_CMD:swu`, implemented creation of boot-slot filesystem artifact `nextoomio-boot.vfat` populated with firmware, kernel (`Image`), device tree blob (`bcm2711-rpi-4-b.dtb`), device tree overlays (`overlays/*`), firmware configuration (`config.txt`), kernel command line (`cmdline.txt`), and derived hardware overlay (`nextoomio-hardware.txt`). Compressed boot artifact to `nextoomio-boot.vfat.gz`.
   - Enforced slot and staging size limits per [ARCHITECTURE.md](../../../ARCHITECTURE.md) section 3.6 step 2:
     - Boot slot: `NEXTOOMIO_BOOT_SLOT_MAXSIZE = "268435456"` (256 MiB).
     - Root slot: `NEXTOOMIO_ROOT_SLOT_MAXSIZE = "3221225472"` (3072 MiB = 3 GiB).
     - Staging reservation: `NEXTOOMIO_STAGING_RESERVATION_MAXSIZE = "1073741824"` (1024 MiB = 1 GiB).
     - Expanded uncompressed sizes are validated against their slot limits; aborts build with `bbfatal` if any artifact or update container exceeds its capacity (AC3).
   - Generated `sw-description` containing `version = "${DISTRO_VERSION}"`, `description = "nextoomio system update image"`, `hardware-compatibility: [ "${NEXTOOMIO_HW_COMPATIBILITY}" ]` (`raspberrypi4-64`), readable schema range `config-schema-range = "1..1"`, `config-schema-min = "1"`, `config-schema-max = "1"`, SHA-256 for boot-slot artifact, SHA-256 for root-slot artifact (`nextoomio-image-raspberrypi4-64.rootfs.ext4.gz`), and dual-slot selections (`copy1` targeting `/dev/mmcblk0p2` & `/dev/mmcblk0p5`, `copy2` targeting `/dev/mmcblk0p3` & `/dev/mmcblk0p6`).
   - Packaged files into `.swu` container via `cpio -ov -H crc` with `sw-description` as the mandatory first file.
   - Enforced unsigned updates without signing keys (`SWUPDATE_SIGNING = ""`, UPD-03, AC2).

2. **SWUpdate runtime package configuration and hardware identification (AC1, AC2):**
   - Created `meta-nextoomio/recipes-support/swupdate/swupdate_%.bbappend` setting `SWUPDATE_SIGNING = ""` and installing `/etc/swupdate.cfg` and `/etc/hwrevision`.
   - Created `meta-nextoomio/recipes-support/swupdate/files/hwrevision` containing `raspberrypi4-64 1.0` to match the `hardware-compatibility` declaration in `sw-description`.
   - Created `meta-nextoomio/recipes-support/swupdate/files/swupdate.cfg` with verbose logging and without cryptographic signature checking.
   - Created `meta-nextoomio/recipes-support/swupdate/nextoomio-update-image.bb` inheriting `swupdate` to provide a dedicated update image recipe.
   - Created `meta-nextoomio/recipes-support/swupdate/files/sw-description` template.

3. **Distro and image configuration updates (AC1, AC4, D-008):**
   - Appended `image_types_nextoomio` to `IMAGE_CLASSES` in `meta-nextoomio/conf/distro/nextoomio.conf`.
   - Appended `swu` to `IMAGE_FSTYPES` in `meta-nextoomio/recipes-core/images/nextoomio-image.bb` (`IMAGE_FSTYPES = "wic.bz2 wic.bmap ext4.gz swu"`), ensuring both flashable image (`wic.bz2`) and update container (`.swu`) are generated with identical `DISTRO_VERSION` (`0.0.1-dev`).
   - Clarified description in `meta-nextoomio/README.md` to distinguish Phase 0 components (`nx-sysd`) from v0.0.1 planned components (D-008).

4. **Kas and CI workflow updates (AC5):**
   - Updated `kas/base.yml` target to build both `nextoomio-image` and `nextoomio-update-image`.
   - Updated `.github/workflows/yocto-build.yml` in parse-only verification to check both `nextoomio-image` and `nextoomio-update-image`.
   - Updated `.github/workflows/yocto-build.yml` artifact upload step to publish `build/**/deploy/images/raspberrypi4-64/*.swu` next to `*.wic.bz2` under artifact `nextoomio-rpi4-64-${{ github.sha }}`.

5. **Static validation and automated self-tests:**
   - Extended `scripts/check_yocto_layer.py` with validation checks for `image_types_nextoomio.bbclass`, `swupdate_%.bbappend`, `nextoomio-update-image.bb`, `sw-description`, `swupdate.cfg`, `hwrevision`, size limits, and CI workflow artifact upload paths.
   - Added 8 automated self-tests (tests 18–25, 25 total) in `scripts/check_yocto_layer.py --test` verifying that failures are triggered when `swu` is missing from `IMAGE_FSTYPES`, when `hardware-compatibility`, `config-schema-range`, or `sha256` are missing, when size limits are altered, when signing is enabled, or when `*.swu` artifact upload is omitted.
   - Ran `make check` including `check-docs`, `check-doc-versions`, `check-evidence`, `check-i18n`, and `yocto-validate`.
   - Ran `make check-core` and `make test-core`.
