## Procedure

1. **SWUpdate update file type and packaging class (AC1, AC2, AC3, D-008, D-056):**
   - Maintained `meta-nextoomio/classes/image_types_nextoomio.bbclass` inheriting `image_types` providing image type `swu` with dependency `IMAGE_TYPEDEP:swu = "ext4.gz"` as the single producer of the update file.
   - In `IMAGE_CMD:swu`, implemented creation of boot-slot filesystem artifact `nextoomio-boot.vfat` populated with firmware, kernel (`Image`), device tree blob (`bcm2711-rpi-4-b.dtb`), device tree overlays (`overlays/*`), firmware configuration (`config.txt`), kernel command line (`cmdline.txt`), and derived hardware overlay (`nextoomio-hardware.txt`).
   - Boot artifact alignment with flashable image (AC4; expected from the code, not yet shown on hardware): The update file's boot slot (`nextoomio-boot.vfat`) is configured to be populated with the same set of boot files deployed for `IMAGE_BOOT_FILES_label-boot_a` in the flashable image: kernel (`Image`), device tree blob (`bcm2711-rpi-4-b.dtb`), bootloader firmware files (`bcm2835-bootfiles/*`), device tree overlays (`overlays/*`), boot configuration (`config.txt`), kernel arguments (`cmdline.txt`), and derived audio hardware profile overlay (`nextoomio-hardware.txt`). Because both `bootimg-partition` (in Wic for slot A) and `IMAGE_CMD:swu` (for the update file) are configured to consume the identical deployed files from `${DEPLOY_DIR_IMAGE}` produced by the same BitBake build, both slot A and slot B boot filesystems are structurally and functionally equivalent as designed (verification on physical device not yet shown; see Missed targets).
   - Added task file dependency `do_image_swu[file-checksums] += "${SWUPDATE_DESCRIPTION_TEMPLATE}:True"` so that changes to the template file `sw-description.in` trigger rebuild of the `.swu` container.
   - Hardened boot-slot assembly: enforced checks with `bbfatal` when required boot files (`Image`, `bcm2711-rpi-4-b.dtb`, `cmdline.txt`, `config.txt`, `nextoomio-hardware.txt`) are absent (CQ-R2, D-056); removed `|| true` guards from `mcopy` and `mmd` so file copy failures fail the build fatally; configured `mkfs.vfat -F 32 -n "boot" -C "${BOOT_ARTIFACT}" 262144` (262144 1 KiB blocks = 268435456 B) fitting exactly the 256 MiB `boot_a`/`boot_b` slot capacity in [ARCHITECTURE.md](../../../ARCHITECTURE.md) section 3.6. Compressed boot artifact to `nextoomio-boot.vfat.gz`.
   - Enforced slot and staging size limits per [ARCHITECTURE.md](../../../ARCHITECTURE.md) section 3.6 step 2:
     - Boot slot: `NEXTOOMIO_BOOT_SLOT_MAXSIZE = "268435456"` (256 MiB).
     - Root slot: `NEXTOOMIO_ROOT_SLOT_MAXSIZE = "3221225472"` (3072 MiB = 3 GiB).
     - Staging reservation: `NEXTOOMIO_STAGING_RESERVATION_MAXSIZE = "1073741824"` (1024 MiB = 1 GiB).
     - Expanded uncompressed sizes are validated against their slot limits (using `stat -c %s` or stream counting `gzip -dc | wc -c` to avoid 32-bit modulo wrapping); aborts build with `bbfatal` if any artifact or update container exceeds its capacity (AC3).
   - Configured `NEXTOOMIO_HW_REVISION = "1.0"` and `NEXTOOMIO_HW_COMPATIBILITY = "${NEXTOOMIO_HW_REVISION}"` so that `hardware-compatibility` in `sw-description` lists `[ "1.0" ]` matching the revision field of `/etc/hwrevision` (`raspberrypi4-64 1.0`).
   - Populated `sw-description` via `sed` substitutions from template file `meta-nextoomio/recipes-support/swupdate/files/sw-description.in`, avoiding heredocs and unindented column-0 lines inside `IMAGE_CMD:swu` that cause BitBake parser failures. Version is taken dynamically from `${DISTRO_VERSION}` (AC1, AC4).
   - Packaged files into `.swu` container via `cpio -ov -H crc` with `sw-description` as the mandatory first file.
   - Enforced unsigned updates per UPD-03 and AC2: packaging strictly archives `sw-description`, `${BOOT_PKG_FILE}`, and `${ROOT_PKG_FILE}` via cpio without creating or packaging `sw-description.sig`, and requiring no signing keys. Removed unused `SWUPDATE_SIGNING` declarations.

2. **SWUpdate runtime package configuration and single producer cleanup (AC1, AC2, CQ-R14):**
   - Maintained `meta-nextoomio/recipes-support/swupdate/swupdate_%.bbappend` installing `/etc/swupdate.cfg` and `/etc/hwrevision`.
   - Maintained `meta-nextoomio/recipes-support/swupdate/files/hwrevision` containing `raspberrypi4-64 1.0` where `raspberrypi4-64` is the board name and `1.0` is the hardware revision matched against `hardware-compatibility` in `sw-description`.
   - Maintained `meta-nextoomio/recipes-support/swupdate/files/swupdate.cfg` with verbose logging, omitting unused Hawkbit `identify` section.
   - Maintained `meta-nextoomio/recipes-support/swupdate/files/sw-description.in` configuring dual-slot selections (`stable.copy1` for slot A `/dev/mmcblk0p2` & `/dev/mmcblk0p5`, and `stable.copy2` for slot B `/dev/mmcblk0p3` & `/dev/mmcblk0p6`) without a top-level `images` list that would unconditionally write to slot A (CQ-R1, CQ-R14).
   - Removed competing recipe `meta-nextoomio/recipes-support/swupdate/nextoomio-update-image.bb` and redundant `SWUPDATE_IMAGES*` variables in `meta-nextoomio/conf/distro/nextoomio.conf`, ensuring `nextoomio-image` is the single producer of `.swu`.

   - Configured `.github/workflows/yocto-build.yml` artifact upload step to publish `build/**/deploy/images/raspberrypi4-64/*.swu` next to `*.wic.bz2` under artifact `nextoomio-rpi4-64-${{ github.sha }}`.
