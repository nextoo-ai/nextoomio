# Evidence: D-065 nx-sysd update commands have no lock between processes

> [!IMPORTANT]
> Secrets, private keys, credentials, tokens, passwords, and addresses of private networks must not be recorded in evidence.

- **Date:** 2026-11-17
- **Image version and commit:** none (repository only); commit {{COMMIT}}
- **Hardware model and revision:** none (repository only); macOS workstation (Darwin 27.0.0, rustc 1.94.1)
- **Physical access needed:** none

## Procedure

All checks ran on the workstation from the repository root, on branch `dev/254-nx-sysd-transition-lock` based on `36c5627`.

1. `cargo test --locked --manifest-path core/Cargo.toml -p nx-sysd` (the process tests also ran three more times in a row with `cargo test -p nx-sysd --bin nx-sysd`).
2. `cargo test --locked --manifest-path core/Cargo.toml` (whole workspace).
3. `make check-core` (cargo check and clippy with `-D warnings`) and `make check`.

The tests for the criteria are in `core/crates/nx-sysd/src/process_tests.rs`. Each test starts the test executable again as separate operating-system processes that share only a temporary update directory and a temporary selector directory:

- `cli` children run an `nx-sysd update …` command line through the same dispatch function `main` uses, with the physical slot backend (`NEXTOOMIO_SLOT` and `NEXTOOMIO_SELECT_DIR` point it at the temporary directories).
- `hold-lock` children take the updater lock (`flock` on `<update dir>/.lock`), optionally record the remote confirmation under it, and hold it for a fixed time.
- `watchdog` children run `UpdateEngine::run_trial_watchdog`, the method `nx-sysd update trial-watchdog` calls, on the shared journal and staging files with the mock slot backend, because the physical local health check needs a device (`/data` mounted, an openable sound card).

## Observed result

| Criterion | Test and observed result |
| --- | --- |
| AC1 | `ac1_second_upload_process_is_refused_while_the_first_is_open`: process 1 runs `update stage --file /dev/stdin` and receives 3000 bytes, then its upload stays open (journal `receiving`). Process 2 runs `update stage --file second.swu`: exit code 1, stderr contains `update_busy`, and every file in the update directory is byte-for-byte as before it ran. Process 1 then receives 2000 more bytes and ends successfully: journal `staged` at the next generation, length 5000, and the SHA-256 of the first upload's bytes; `staging.swu` starts with those bytes. Passed. |
| AC2 | `ac2_killed_lock_holder_releases_the_lock_and_keeps_the_journal`: the upload process is killed (`SIGKILL`) while `receiving` and holding the lock. The test process then takes the lock at once; `update status --json` reports `receiving`, and the journal record equals the one read before the kill. `update init-staging` takes the lock and moves the journal one generation on to `failed` with `update_truncated`. Passed. |
| AC3 | `ac3_status_answers_while_another_process_holds_the_lock`: while a third process holds the lock for 3 s, `update status --json` exits 0 within 2.5 s with `idle`, and `update abort` exits 1 with `update_busy` without changing any file. `ac3_status_leaves_an_uninitialized_directory_unchanged`: for a missing update directory, `status --json` reports `"initialized": false` and the directory is not created; for a directory holding only a zero-filled `journal.0`, `status` and `status --json` leave every file byte-for-byte unchanged (no `journal.1`, `.lock`, or staging files appear), and the text output says `State: not initialized`. Passed. |
| AC4 | `ac4_watchdog_and_separate_confirm_process_commit`: a trial of slot B with remote confirmation runs in a watchdog process; a third process holds the lock for 1 s; a separate `update confirm --transaction tx-d065 --wait 30 --json` process reports `Updater lock busy; retrying every 200 ms`, records the confirmation after the lock is released, and exits 0 with `committed`. The watchdog process exits 0; the journal is `committed`, default slot `root_b`, confirmed. `ac4_watchdog_retries_while_a_third_process_holds_the_lock`: a third process records the confirmation under the lock and keeps holding it for 1.5 s; 500 ms into that hold the journal is still `trial`. The watchdog process reports `Updater lock busy; retrying the commit every 200 ms`, does not fail the trial, and commits after the lock is released (exit 0, journal `committed`, default slot `root_b`). Passed. |

Whole runs: `nx-sysd` library tests 80 passed, process tests 7 passed (and 7 passed in each of three repeated runs); whole workspace all passed; `make check-core` exit 0; `make check` exit 0.

## Missed targets

- Not run on a device or on Linux: the lock was observed only on macOS, where `File::try_lock` is `flock(LOCK_EX | LOCK_NB)` as on Linux. Behaviour on the device's ext4 `/data` is not observed.
- The trial service in AC4 ran with the mock slot backend, so the physical health check, the hardware watchdog device, the selector write, and the reboot paths were not exercised in these process tests. `update trial-watchdog` itself (the CLI path with the physical backend) was not run as a process.
- The retry of engine loading on a busy lock in `update trial-watchdog` (when the update directory needs initialization at boot) is not covered by a test.
- An upload interrupted by a killed process leaves the journal `receiving`; a later `update stage` is still refused as busy by the state check until boot reconciliation (`update init-staging`) ends the transaction, as before this change.
