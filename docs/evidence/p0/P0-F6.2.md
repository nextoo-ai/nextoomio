## Procedure

1. **Test tone generation with strictly bounded safe signal level (AC2, D-012):**
   - Implemented `meta-nextoomio/recipes-nextoomio/nextoomio-tone-check/files/generate-tone.py`.
   - Generated a 2.0-second 48 kHz stereo WAV file with a 440 Hz tone, alternating channels (0.0–1.0s Left channel active, Right channel silent; 1.0–2.0s Left channel silent, Right channel active) to verify both stereo channels and prepare for listening verification (P0-F6.3).
   - Enforced safe signal level in the tool itself: peak amplitude is bounded to linear gain $0.02700$ ($-31.37$ dBFS), corresponding to the default 30% logical volume under the shared cubic gain curve ($V = 30\% \implies \text{gain} = (0.3)^3 = 0.027$, SPECIFICATION.md section 3, ARCHITECTURE.md section 3.2). For 16-bit signed PCM, peak amplitude is strictly $\le 885$ ($885 / 32767 = 0.0270$). Direct playback to passive speakers on the bench is protected against unattenuated output (D-012).
   - Added verification mode (`generate-tone.py --check <file>`) to ensure all generated and installed tones comply with sample rate, frame count, channel, and amplitude constraints.

2. **Command-line remote tone check utility (AC1, AC3, AC4, D-012):**
   - Implemented `meta-nextoomio/recipes-nextoomio/nextoomio-tone-check/files/nextoomio-tone-check.sh` installed to `/usr/bin/nextoomio-tone-check`.
   - Evaluated ALSA sound card presence via `/proc/asound/cards` against the active hardware profile (`/etc/nextoomio/hardware-profile.json`, `alsa_card_id: "sndrpihifiberry"`); if absent, fails with distinct exit code `2` and reason `sound_card_absent` (AC3).
   - Evaluated whether the ALSA PCM device is busy before and during playback via `/proc/asound/card<idx>/pcm0p/sub0/status` and `aplay` error diagnostics; if busy, fails with distinct exit code `3` and reason `playback_device_busy` (AC3).
   - Configured signal and exit cleanup traps (`INT`, `TERM`, `HUP`, `EXIT`) ensuring that if the check ends in any way, the background player is terminated and no stream is left open (AC4).
   - Initiated playback via `aplay -D plughw:<card>,0` and polled `/proc/asound/card<idx>/pcm0p/sub0/status` during playback: verified that `state: RUNNING` was observed and that `hw_ptr` advanced by the expected number of frames ($96,000$ frames at 48 kHz for 2.0s, requiring $\ge 86,400$ frames threshold accounting for drain latency). Exits with distinct code `4` if the stream failed to reach `RUNNING` or hardware position did not advance (AC1).
   - Supported `--json` output for structured machine readability and `--quiet` for non-interactive scripting.

3. **BitBake recipe and image integration (AC1, AC2):**
   - Created `meta-nextoomio/recipes-nextoomio/nextoomio-tone-check/nextoomio-tone-check_0.0.1.bb` inheriting nothing external, using `python3` in `do_compile` to generate and verify `test-tone-48k-440hz.wav`, installing `/usr/bin/nextoomio-tone-check` and `/usr/share/nextoomio/tone-check/test-tone-48k-440hz.wav`, with `RDEPENDS:${PN} = "alsa-utils"`.
   - Updated `meta-nextoomio/recipes-core/images/nextoomio-image.bb` appending `nextoomio-tone-check` to `IMAGE_INSTALL`.

4. **Bench tooling and deploy integration (AC5):**
   - Created `scripts/bench/tone-check.sh` allowing workstation execution of the remote tone check over SSH (`ssh <host> nextoomio-tone-check`).
   - Created `scripts/bench/deploy.sh` incorporating the deploy confirmation workflow with an optional `--tone-check` parameter (AC5) that runs the tone check as the final verification step after confirming the new slot, including the tone check output in the deploy output.

5. **Automated validation and self-tests:**
   - Extended `scripts/check_yocto_layer.py` with static layer validation and 5 new automated self-tests (tests 18–22, bringing total to 22 self-tests) verifying rejection of missing tone check in image install, unattenuated volume generation, missing absent card detection (code 2), missing busy device detection (code 3), and missing deploy `--tone-check` option.
   - Executed `make check` (traceability, doc versions, evidence, i18n, yocto validation) and core Rust checks (`make check-core`, `make test-core`).

## Missed targets

In accordance with the project owner's decision of 2026-11-15 and the Architect's instructions for issue #29, all Phase 0 software is implemented and statically verified first in author sessions, while full image builds and hardware measurements run on `main` and the bench device afterwards. The following items require an image build and physical bench hardware:
- **Build verification:** BitBake image build (`kas build kas/rpi4-64.yml`) to produce the release image containing `/usr/bin/nextoomio-tone-check` and `/usr/share/nextoomio/tone-check/test-tone-48k-440hz.wav` will be verified on `main`.
- **AC1:** Runtime tone check execution on physical Raspberry Pi 4 + HiFiBerry Amp+ bench hardware to verify that the kernel ALSA driver advances hardware positions using the hardware I2S bit clock for the 2.0s duration.
- **AC2:** Electrical measurement of physical amplifier speaker output terminals to confirm peak voltage level corresponds to 30% volume limit.
- **AC3:** Runtime physical checks with disconnected sound card overlay or concurrent PipeWire/MPD stream holding the ALSA device open on bench hardware.
- **AC4:** Physical listening verification that speaker is completely silent after the tone check terminates.
- **AC5:** End-to-end bench deploy over SSH to physical bench hardware followed by automated post-deploy tone check.
