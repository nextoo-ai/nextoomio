## Procedure

1. **Release metadata configuration and build-time generation (AC1, AC4):**
   - Configured `meta-nextoomio/conf/distro/nextoomio.conf` with distro defaults: `NEXTOOMIO_IMAGE_VERSION ?= "${DISTRO_VERSION}"`, `NEXTOOMIO_BUILD_ID ?= "${DATETIME}"`, and `NEXTOOMIO_HARDWARE_COMPAT ?= "raspberrypi4-64"`.
   - Created `meta-nextoomio/recipes-core/os-release/os-release.bbappend` appending `BUILD_ID`, `IMAGE_VERSION`, `NEXTOOMIO_BUILD_ID`, `NEXTOOMIO_SOURCE_COMMIT`, `NEXTOOMIO_IMAGE_VERSION`, and `NEXTOOMIO_HARDWARE_COMPAT` to `OS_RELEASE_FIELDS`, and generating `/etc/nextoomio-release` with image release metadata.
   - Created `meta-nextoomio/classes/nextoomio-image-version.bbclass` hooked into `IMAGE_PREPROCESS_COMMAND` to ensure `/etc/nextoomio-release` is staged in the target root filesystem, and inherited it in `meta-nextoomio/recipes-core/images/nextoomio-image.bb`.
   - Implemented release file parsing in `core/crates/nx-sysd/src/identity.rs` supporting both standard `/etc/os-release` and `/etc/nextoomio-release` formats.

2. **Hardware identity reporting (AC2):**
   - Implemented board model detection in `core/crates/nx-sysd/src/identity.rs` inspecting `/proc/device-tree/model` and `/sys/firmware/devicetree/base/model` with fallback to reference target `"Raspberry Pi 4 Model B"`.
   - Implemented hardware-compatibility reporting matching the target architecture string (`"raspberrypi4-64"`) used by SWUpdate update container validation (UPD-04).
   - Provided CLI command `nx-sysd hardware` and `--hardware` flag emitting hardware identity as JSON.

3. **Persistent device ID generation on data partition (AC3):**
   - Updated `meta-nextoomio/recipes-core/base-files/base-files_%.bbappend` ensuring the persistent mount point `${D}/data` exists and adding `LABEL=data /data ext4 defaults,noatime 0 2` to `${D}${sysconfdir}/fstab`.
   - Created systemd one-shot service `meta-nextoomio/recipes-nextoomio/nx-sysd/files/nextoomio-device-id.service` executing `/usr/bin/nx-sysd init-device-id` ordered after `data.mount` and before `basic.target`/`multi-user.target`.
   - Updated `meta-nextoomio/recipes-nextoomio/nx-sysd/nx-sysd_0.0.1.bb` inheriting `systemd`, enabling `nextoomio-device-id.service`, and packaging the service unit.
   - Implemented cryptographically random UUIDv4 generation (`generate_random_uuid_v4`) reading from `/dev/urandom` and atomic persistence to `/data/device-id` (`get_or_create_device_id`). If `/data/device-id` exists, it is read without modification, ensuring persistence across reboots, slot B updates, and rollbacks.

4. **Single JSON identity command and slot detection (AC1, AC2, AC3, AC4):**
   - Implemented running slot detection in `core/crates/nx-sysd/src/identity.rs` inspecting `/proc/cmdline` for partition 5 (`4e58544d-05`, `mmcblk0p5`, `root_a` -> slot A) and partition 6 (`4e58544d-06`, `mmcblk0p6`, `root_b` -> slot B), falling back to `/proc/mounts` root mount entry or slot A default.
   - Implemented `nx-sysd identity` (also executed when `nx-sysd` is invoked with no arguments or through symlink `/usr/bin/nx-identity`) outputting complete identity JSON: `image_version`, `source_commit`, `build_id`, `running_slot`, `board_model`, `hardware_compatibility`, and `device_id`.
   - Created `/usr/bin/nx-identity` symlink in `nx-sysd_0.0.1.bb` for direct invocation over SSH by remote deploy tooling.

5. **Static layer checks and unit verification:**
   - Extended `scripts/check_yocto_layer.py` validating the presence and contents of `os-release.bbappend`, `nextoomio-image-version.bbclass`, `nextoomio-device-id.service`, `nx-sysd_0.0.1.bb`, and `/data` mount configuration in `base-files_%.bbappend`.
   - Implemented 7 unit tests in `core/crates/nx-sysd` covering release file parsing, slot detection, device ID generation and persistence, differing image builds (AC4), hardware identity (AC2), and full identity JSON schema (AC1–AC3).
   - Executed local verification suite: `make check`, `python3 scripts/check_yocto_layer.py`, `python3 scripts/check_evidence.py`, `make check-core`, and `make test-core`.

## Missed targets

In accordance with the project owner's decision of 2026-11-15 and the Architect's instructions for issue #13, all Phase 0 software is implemented and statically verified first in author sessions, while full image builds and hardware measurements run on `main` and the bench device afterwards. The following items require an image build and physical bench hardware:
- **Build verification:** Full BitBake image build on `main` validating `os-release.bbappend`, `nextoomio-image-version.bbclass`, and compilation of `nx-sysd` with `nextoomio-device-id.service`.
- **AC1:** Runtime SSH query of `nx-sysd version` and `nx-sysd identity` on physical bench device running slot A and slot B.
- **AC2:** Runtime devicetree model verification on physical Raspberry Pi 4 Model B bench hardware.
- **AC3:** First-boot verification on real card confirming `/data/device-id` generation and persistence across reboot, update, and rollback.
- **AC4:** Dual-slot update deployment verifying differing versions reported between slot A and slot B.
