## Procedure

1. **Read-only root filesystem and active boot partition configuration (AC1, SYS-04, ARCHITECTURE.md sections 3.5 & 3.6):**
   - Configured `IMAGE_FEATURES += "read-only-rootfs"` in `meta-nextoomio/recipes-core/images/nextoomio-image.bb`.
   - Created `meta-nextoomio/recipes-core/base-files/base-files_%.bbappend` ensuring `/boot/select` and `/data` mountpoints are created in the base filesystem via `dirs755:append = " /boot/select /data"`.
   - Configured `meta-nextoomio/recipes-core/base-files/files/fstab` mounting:
     - Root filesystem `/dev/root` read-only (`ro,noatime,errors=remount-ro 0 1`).
     - Selector partition `LABEL=select /boot/select` read-only (`ro,defaults,nofail 0 0`).
     - Persistent data partition `LABEL=data /data` (`defaults,noatime,nofail 0 0`).
     - Omitted static `/boot` mount from `fstab` to avoid hard-wiring slot A.
   - Configured `--no-fstab-update` in `meta-nextoomio/files/wic/nextoomio-ab.wks.in` for `part /boot/select`, `part /boot`, and `part /data` to prevent wic from appending conflicting read-write defaults to the rootfs `/etc/fstab`.
   - Created `nextoomio-boot-mount.sh` and systemd unit `nextoomio-boot-mount.service` (ordered before `local-fs.target`) to dynamically resolve the active boot partition (`boot_a` if root is slot A, `boot_b` if root is slot B) and mount it read-only (`ro,defaults,nofail`) at `/boot`.
   - Verified that mounts are configured with read-only (`ro`) mount options; live write rejection (EROFS) is recorded as a missed target pending physical hardware bench execution.

2. **Wic layout and first-boot data partition expansion (AC2, D-006, ARCHITECTURE.md section 3.6):**
   - Updated `meta-nextoomio/files/wic/nextoomio-ab.wks.in` partition 7 (`/data`) from `--fixed-size 1536M` to `--size 1536M --no-fstab-update`, allowing the partition to be expanded beyond initial image capacity to the remainder of the card (resolving defect D-006) without wic injecting duplicate fstab lines. Initial configured size is 1536 MiB.
   - Created `meta-nextoomio/recipes-nextoomio/nextoomio-data/files/nextoomio-data-grow.sh` and corresponding systemd service `nextoomio-data-grow.service`:
     - Inspects disk and partition geometry via sysfs (`/sys/class/block/<disk>/size` vs. `/sys/class/block/<part>/start + size`).
     - Checks whether ext4 filesystem needs expansion by comparing filesystem size (`dumpe2fs -h` / `tune2fs -l` block count) with partition capacity (`blockdev --getsize64` or sysfs).
     - On first boot with free disk space > 8192 sectors (4 MiB), resizes extended partition 4 and logical partition 7 to 100% using `parted` (or `sfdisk`), informs the kernel via `partx -u`, and expands ext4 using `resize2fs`.
     - In the recovery case where the partition table was already extended to the end of the card but `resize2fs` failed or was interrupted, detects that the filesystem is smaller than the partition (`FS_DIFF > 4 MiB`), skips `parted`, and executes `resize2fs`. All commands check exit status and surface failures.
     - On second and subsequent boots where both partition geometry and filesystem size fill the disk, exits immediately without re-running resize operations, guaranteeing idempotency.
     - Service ordering and safety: `nextoomio-data-grow.service` is ordered `Before=nextoomio-data-check.service data.mount local-fs-pre.target` (`After=systemd-udev-settle.service`). On first boot of a freshly flashed image, the unmounted ext4 filesystem created by wic is clean and has never been mounted, allowing `resize2fs` to operate cleanly without prior check. Running grow before `nextoomio-data-check.service` ensures that `nextoomio-data-check` (`e2fsck -p -f`) then verifies the final, expanded filesystem before `data.mount` mounts it.

3. **Pre-mount data partition check and repair (AC3, ARCHITECTURE.md section 3.5):**
   - Created `meta-nextoomio/recipes-nextoomio/nextoomio-data/files/nextoomio-data-check.sh` and systemd unit `nextoomio-data-check.service` ordered `Before=data.mount local-fs.target` and `After=nextoomio-data-grow.service`.
   - Executes `e2fsck -p -f` on `/dev/disk/by-label/data` before mount on every boot, automatically repairing harmless corruptions (exit codes 0 or 1).
   - In `fstab`, configured `LABEL=data` with `nofail` and passno 0 so standard systemd does not abort boot or enter emergency mode on severe corruption.

4. **Persistent directory hierarchy, ownership, and permissions (AC4, ARCHITECTURE.md section 3.5):**
   - Created `meta-nextoomio/recipes-nextoomio/nextoomio-data/files/nextoomio-data-init.sh` and systemd unit `nextoomio-data-init.service` ordered `Wants=data.mount`, `After=data.mount`, and `Before=multi-user.target`.
   - Creates and enforces permissions for required subtrees:
     - `/data/config`: mode `0755`, ownership `root:root`.
     - `/data/secrets`: mode `0700`, ownership `root:root` (explicitly not world-readable, preventing world access).
     - `/data/music`: mode `0755`, ownership `root:root`.
     - `/data/update`: mode `0755`, ownership `root:root`. Preallocates fixed-capacity staging file `/data/update/staging.swu` (1 GiB) and dual journal records `/data/update/journal.0` and `journal.1` (64 KiB each) with real allocated disk blocks (verified non-sparse via `st_blocks > 0`); detects and re-creates mismatched or incomplete files.
     - `/data/log`: mode `0755`, ownership `root:root`, containing `/data/log/journal` bind-mounted to `/var/log/journal`.
   - Touches `/data/.initialized`.

5. **Unmountable data partition recovery and reachability (AC5, ARCHITECTURE.md section 3.5):**
   - If `e2fsck` reports severe uncorrectable errors (exit code >= 4) or partition block device is missing, `nextoomio-data-check.sh` records `data_unavailable` in `/run/nextoomio/data_status`, touches `/run/nextoomio/data_unavailable`, and exits 0 to let systemd proceed to `multi-user.target`.
   - Added drop-in `data.mount.d/10-condition.conf` with `ConditionPathExists=!/run/nextoomio/data_unavailable`, preventing systemd from mounting the corrupted filesystem at `/data`.
   - `nextoomio-data-init.sh` detects `data_unavailable` flag or missing mount; it logs recovery mode, provides a volatile in-memory fallback `tmpfs` on `/data` (surfacing any mount failure), and never reformats the physical partition.
   - Production image (`nextoomio-image.bb`) excludes SSH server per ARCHITECTURE.md section 3.7. Development image variant (`nextoomio-image-dev.bb`) enables OpenSSH server (`ssh-server-openssh`) to ensure development images remain reachable over SSH when reaching `multi-user.target`.

6. **Log storage bounds and persistent log ring (AC6, ARCHITECTURE.md section 3.5):**
   - Created `meta-nextoomio/recipes-core/systemd/systemd-conf_%.bbappend` and drop-in configuration `meta-nextoomio/recipes-core/systemd/files/10-nextoomio-journald.conf`:
     - `Storage=persistent`
     - `RuntimeMaxUse=32M`, `RuntimeMaxFileSize=4M` (bounds volatile in-memory storage)
     - `SystemMaxUse=32M`, `SystemMaxFileSize=4M` (bounds persistent log ring in `/data/log`)
     - `MaxRetentionSec=1month`
   - In read-only rootfs, `/var/log` resides on volatile tmpfs storage (`/var/volatile`), which is writable. `nextoomio-data-init.sh` creates `/var/log/journal`, bind-mounts `/data/log/journal` to `/var/log/journal` (surfacing any bind-mount failure as an error), and flushes journald with `killall -USR1 systemd-journald` (or `systemctl kill`).
   - Removed obsolete `VOLATILE_LOG_DIR` from distro configuration.

7. **Packaging, validation, and test suite:**
   - Created `meta-nextoomio/recipes-nextoomio/nextoomio-data/nextoomio-data_0.0.1.bb` inheriting `systemd`, declaring runtime dependencies on `e2fsprogs-e2fsck`, `e2fsprogs-resize2fs`, `e2fsprogs-tune2fs`, `parted`, `util-linux-partx`, `util-linux-blockdev`, and `util-linux-fallocate`, using `S = "${WORKDIR}/sources"` and `UNPACKDIR = "${S}"` for BitBake Scarthgap/Wrynose compatibility, and registering all 4 systemd services and the `data.mount` condition drop-in.
   - Updated `meta-nextoomio/recipes-core/images/nextoomio-image.bb` to install `nextoomio-data`, `e2fsprogs-e2fsck`, `e2fsprogs-resize2fs`, and `parted`.
   - Extended `scripts/check_yocto_layer.py` to validate `nextoomio-data` recipe, base-files append, systemd-conf drop-in, `data.mount.d/10-condition.conf`, Wic `/data` non-fixed size, `--no-fstab-update` on `/boot/select`, `/boot`, and `/data`, recipe absence of `S = "${WORKDIR}"`, and image package installation.
   - Created unit test suite `scripts/test_data_partition.py` executing real shell scripts in isolated test environments using PATH stubs (no mock hooks in production code): syntax check (`sh -n`), dynamic active boot slot resolution (`boot_a` vs `boot_b`), first-boot expansion, second-boot idempotency via sysfs geometry and filesystem size, expansion when partition is grown but filesystem is not, expansion failure surfacing (parted and resize2fs), pre-mount e2fsck handling (exit codes 0, 1, and 4), `data.mount` condition drop-in validation, directory creation and permissions (`0700` and world-bits `0`), real block preallocation (`st_blocks > 0`) and healing, recovery mode handling and tmpfs failure surfacing, and journald bounds configuration (14 tests total).
   - Ran `make check`, `make yocto-validate`, and `python3 scripts/test_data_partition.py`.
