## Procedure

1. **Implementation of automated ten-cycle update soak tool (`scripts/bench/soak.py`):**
   - Implemented `SoakRunner` executing automated consecutive update cycles between two distinguishable valid images (`image_a.swu` and `image_b.swu`) on the bench device:
     - Pre-flight checks: parses `sw-description` inside both images to extract release versions, verifying $V_A \neq V_B$.
     - Validates bench device SSH reachability and queries initial slot and version.
     - Alternates deployment between Image A and Image B across cycles 1..10 (AC1).
     - Verifies AC1 invariants on each cycle:
       - Deployment succeeds and remote confirmation transitions update state to `committed`.
       - Active slot alternates each cycle (`root_a` <-> `root_b`) without repetition.
       - Reported version matches deployed image version.
     - Implemented `MarkerManager` (AC3) writing a unique token, timestamp, and SHA-256 checksum to `/data/nextoomio-soak-marker.txt` before cycle 1, verifying checksum and content after each cycle and at run completion to prove persistent `/data` partition preservation across 10 A/B cycles.
     - Implemented diagnostic halting (AC4) stopping immediately if any cycle or step fails (upload error, validation error, install error, device timeout, rollback, version mismatch, or marker corruption), naming the failing cycle and step, recording the failure diagnosis, and reporting overall status as `FAILED` with exit code 1.
     - Implemented automated report generator (`SoakReport`, AC2) outputting a dated Markdown/JSON/text soak report with per-cycle step times (`upload`, `validate`, `install`, `wait_for_device`, `confirm`, `marker_check`, `cycle_total`), total duration, and initial/final state.
     - Implemented CLI argument parsing with host/user validation against option injection (CQ-R7), marker path validation under `/data/`, and credential protection (P0-F5.1 (#25) AC6 / [ARCHITECTURE.md](../../../ARCHITECTURE.md) section 4.1 AD-23).

2. **Implementation of automated self-tests (`scripts/bench/test_soak.py`):**
   - Created in-memory `SoakMockDevice` simulating multi-cycle bench device behavior over SSH.
   - Implemented 15 automated test cases verifying:
     - `test_ac1_and_ac2_ten_cycle_soak_success`: 10 full alternating cycles with slot toggle, version matching, commit confirmation, and Markdown report generation.
     - `test_ac3_marker_written_and_verified_unchanged`: Persistent marker creation and SHA-256 verification across 10 cycles.
     - `test_ac3_marker_corruption_causes_failure`: Marker tampering causes immediate halt at `marker_check`.
     - `test_ac4_failure_during_install_step`: Halts at cycle 4 during install.
     - `test_ac4_failure_during_device_timeout`: Halts at cycle 2 during reboot wait.
     - `test_ac4_slot_alternation_failure`: Halts when slot fails to alternate.
     - `test_ac4_version_mismatch_failure`: Halts on version mismatch.
     - `test_precheck_fails_on_identical_images`: Rejects identical images.
     - `test_cli_parsing_positional_and_options`: Command-line interface argument handling.
     - `test_cq_r7_unsafe_identifiers_rejected`: Host and user option injection rejection.
     - `test_json_and_text_report_outputs`: Serialization format checks.
     - `test_fewer_than_ten_cycles_is_non_passing`: Verifies runs with fewer than 10 cycles are marked non-gate / FAILED with actual cycle count reported.
     - `test_cli_rejects_cycles_less_than_one`: Verifies rejection of cycle counts < 1.
     - `test_marker_status_on_early_precheck_failure`: Verifies marker status is reported as 'not checked' on precheck halt.
     - `test_marker_path_validation`: Verifies CQ-R7 validation of `--marker-path` under `/data/`.

## Missed targets

In accordance with the project owner's decision of 2026-11-15 and the Architect's instructions for issue #27, all Phase 0 software is implemented and statically verified first in author sessions, while full BitBake image builds and hardware measurements on real bench hardware run on `main` and the bench device afterwards. The following items require an image build and physical bench hardware:
- **AC1:** Runtime execution of ten full alternating update cycles between two built release .swu images on the physical Raspberry Pi 4 reference bench device.
- **AC2:** Physical bench timing measurements for real flash write, reboot, and network recovery steps, and verification that the run executes unattended on real hardware without anyone touching the device during the ten cycles.
- **AC3:** Physical microSD block device `/data` filesystem verification across ten real hardware power/reboot cycles.
- **AC4:** Physical recovery and diagnostic reporting from real bench failure injection scenarios.
