## Procedure

1. **Deploy script architecture and CLI implementation (AC1, AC2, AC6):**
   - Implemented workstation deployment script in `scripts/bench/deploy.py` using standard-library Python only.
   - Structured command-line arguments to accept target device and `.swu` file path in either order or via `-d/--device` and `-f/--file` flags, with `--timeout` (default 120.0s, matching [SPECIFICATION.md](../../../SPECIFICATION.md) UPD-06 trial budget), `--poll-interval` (default 2.0s), `--expected-version`, `--no-remote-confirm`, `--json`, and `-v/--verbose`.
   - Built CPIO archive reader (`parse_swu_description`) to extract `sw-description` metadata (release version, target hardware compatibility list) across entries in `.swu` containers without third-party dependencies.
   - Integrated `SystemSshRunner` utilizing the system `ssh` command, batch mode (`-o BatchMode=yes`), and the active SSH agent (`SSH_AUTH_SOCK`). Enforced identifier validation (`^[A-Za-z0-9][A-Za-z0-9._-]*$`) on host and user parameters and inserted `--` before the destination argument to defend against SSH option injection (CQ-R7). Verified by inspecting the SSH argument list, checking stdout/stderr streams, and asserting no created files in the working directory that no credentials, tokens, or private keys are written to disk or printed in command line or console outputs (AC6).
   - Documented that device-side commands (`nx-sysd update stage|validate|install|trial|confirm`, `nx-sysd version --json`, `nx-sysd update status --json`), their output format, and `/etc/nextoomio-release` and `/proc/cmdline` PARTUUID fallbacks are working assumptions for the deploy tool until issue #22 and the update-engine stories define and implement the device contract.

2. **Step timing, sequence orchestration, and confirmation control (AC1, AC2, AC3, AC4, AC5):**
   - Implemented `Deployer` and `StepTimer` executing the full deployment flow:
     - Step 1 `precheck`: Inspects update file, extracts version from `sw-description` (or uses `--expected-version`), failing at `precheck` if no expected version can be determined (AC1, AC3). Records initial device kernel boot ID (`/proc/sys/kernel/random/boot_id`), queries device active slot (`nx-sysd version --json` or `/proc/cmdline`) and version, derives target inactive slot (`opposite_slot`).
     - Step 2 `upload`: Streams `.swu` payload to the temporary upload buffer `/data/update/staging.upload.swu` on the device and invokes `nx-sysd update stage --file ...` to stage it into the preallocated staging area (`/data/update/staging.swu`, UPD-05, AR-08) before removing the temporary buffer.
     - Step 3 `validate`: Invokes `nx-sysd update validate` over SSH. On failure, names step `validate`, halts without sending confirmation, and exits non-zero (AC3).
     - Step 4 `install`: Invokes `nx-sysd update install` to write boot and root partitions of the inactive slot. On failure, halts without confirmation and exits non-zero (AC3).
     - Step 5 `start_trial`: Invokes `nx-sysd update trial --remote-confirm` and triggers one-shot reboot (AD-22).
     - Step 6 `wait_for_device`: First waits until the device drops connection or its boot ID (`/proc/sys/kernel/random/boot_id`) changes before accepting SSH reachability, preventing false rollback detection while `sshd` is shutting down. Polls SSH reachability until device returns within the timeout budget (120s). On timeout, names step `wait_for_device`, halts without confirmation, and exits non-zero (AC3).
     - Step 7 `check_running`: Queries returned slot and version. If previous slot is detected, names step `slot_check`, reports rollback and device update state from journal, and suppresses confirmation (AC4). If version does not match expected version, names step `version_check`, suppresses confirmation, and exits non-zero (AC3).
     - Step 8 `confirm`: When remote confirmation is requested (default), sends `nx-sysd update confirm` over SSH, reads update state from the device, and verifies that the state is `committed` (failing the `confirm` step with a non-zero exit if it is not) (AC1, AD-22).
     - Step 9: Formats human-readable or JSON summary printing previous version, new version, running slot, final state (from device, or `unknown` if unreadable), and elapsed time of each step (AC2).
   - Verified against the mock runner (`MockBenchDevice` in unit tests) that running deploy twice in sequence alternates slots automatically (A -> B, then B -> A) (AC5).

3. **Documentation and CI integration:**
   - Documented tool architecture, security rules, CLI usage, options, failure modes, working assumptions, and timing reports in `scripts/bench/README.md` with cross-references to [ROADMAP.md](../../../ROADMAP.md) section 2.1 and [ARCHITECTURE.md](../../../ARCHITECTURE.md) section 3.6, section 4.1.
   - Added `check-bench` target to `Makefile` and added bench test execution step to `.github/workflows/ci.yml`.

4. **Automated self-tests and validation:**
   - Created test suite in `scripts/bench/test_deploy.py` (and embedded `--test` runner in `scripts/bench/deploy.py`) with deterministic `MockBenchDevice` runner covering all six acceptance criteria (AC1–AC6), option injection defense (CQ-R7), CLI parsing, delayed reboot polling, confirm state validation, and CPIO archive parsing.
   - Ran `python3 scripts/bench/deploy.py --test` (13 tests passed).
   - Ran `make check` including `check-docs`, `check-doc-versions`, `check-evidence`, `check-i18n`, `yocto-validate`, and `check-bench`.

## Missed targets

In accordance with the project owner's decision of 2026-11-15 and the Architect's instructions for issue #25, all Phase 0 software is implemented and statically verified first in author sessions, while full image builds and hardware measurements run on `main` and the bench device afterwards. The following items require an image build and physical bench hardware:
- **Bench device execution:** Running `scripts/bench/deploy.py` against a physical Raspberry Pi 4 + HiFiBerry Amp+ over wired Ethernet using the dedicated bench key in the SSH agent.
- **Hardware timing measurements:** Real-world transfer, flash write, and tryboot reboot timings on the reference SD card and Ethernet link.
- **Hardware rollback injection:** Verifying remote rollback detection against a physical device executing watchdog reset or health check timeout on hardware.
- **Step timeouts and transfer durations:** Upload reuses `--timeout` (the 120s trial budget) as its limit, and install/validate have fixed 60s/30s limits; actual step durations and transfer speeds on bench hardware are unmeasured.
