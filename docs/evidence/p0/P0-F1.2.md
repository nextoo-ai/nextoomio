## Procedure

1. **Workflow execution modes and artifact publishing configuration (AC1):**
   - Configured `.github/workflows/yocto-build.yml` to trigger full-image build (`kas build /work/kas/ci-hosted.yml`) on `push` to `main` for paths `kas/**`, `meta-nextoomio/**`, and `.github/workflows/yocto-build.yml`, and via `workflow_dispatch` with input `mode: full-image`. Pull requests execute fast recipe and layer parse verification (`parse-only`).
   - Concurrency group `yocto-build-${{ github.ref }}` with `cancel-in-progress: true` ensures newer pushes cancel stale running full builds.
   - Configured `actions/upload-artifact@v4` under step `Upload Yocto image, package manifest, SPDX SBOM, and license manifest` to publish:
     - Flashable Wic image: `build/**/deploy/images/raspberrypi4-64/*.wic.bz2`
     - Block map: `build/**/deploy/images/raspberrypi4-64/*.wic.bmap`
     - Rootfs package manifests: `build/**/deploy/images/raspberrypi4-64/*.rootfs.manifest` and `build/**/deploy/images/raspberrypi4-64/*.manifest`
     - SPDX SBOM archive: `build/**/deploy/images/raspberrypi4-64/*.spdx.tar.zst`
     - License manifest: `build/**/deploy/licenses/**/license.manifest`
     named with the commit SHA: `nextoomio-rpi4-64-${{ github.sha }}`.

2. **Size budget guard configuration (AC2):**
   - Configured `IMAGE_ROOTFS_MAXSIZE = "3145728"` in `meta-nextoomio/recipes-core/images/nextoomio-image.bb` matching the 3 GiB (3,145,728 KiB) root slot budget defined in `ARCHITECTURE.md` section 3.6 and `meta-nextoomio/files/wic/nextoomio-ab.wks.in` (`part / --fixed-size 3072M`).
   - OpenEmbedded `image.bbclass` evaluates `IMAGE_ROOTFS_SIZE` (the calculated rootfs size in KiB) against `IMAGE_ROOTFS_MAXSIZE` and terminates the build with a fatal error naming the limit (`The rootfs size %d(K) exceeds IMAGE_ROOTFS_MAXSIZE: %d(K)`) if `IMAGE_ROOTFS_SIZE` exceeds this limit.
   - Added automated static check in `scripts/check_yocto_layer.py` validating that `IMAGE_ROOTFS_MAXSIZE` is defined in `nextoomio-image.bb` with hard assignment `=`.

3. **Pinned layer revisions (AC3):**
   - In `kas/base.yml`, all repository layers (`bitbake`, `openembedded-core`, `meta-yocto`, `meta-openembedded`, `meta-raspberrypi`, `meta-swupdate`) are pinned to immutable 40-character commit hashes.
   - Validated via `scripts/check_yocto_layer.py` that all layer definitions use pinned revisions. Two builds of the same commit check out the exact pinned commit hashes, guaranteeing identical layer revisions across builds.

4. **Automated license gate configuration (AC4):**
   - Configured `INCOMPATIBLE_LICENSE = "AGPL-3.0-only AGPL-3.0-or-later AGPL-1.0-only AGPL-1.0-or-later"` in `meta-nextoomio/conf/distro/nextoomio.conf`, complementing `LICENSE_FLAGS_ACCEPTED:append = " synaptics-killswitch commercial_ffmpeg"`.
   - When a component with an incompatible network-copyleft license (AGPL-1.0 or AGPL-3.0) or unaccepted license flags is introduced, BitBake terminates the build.
   - Added automated static check in `scripts/check_yocto_layer.py` validating that `INCOMPATIBLE_LICENSE` is defined in `nextoomio.conf` with hard assignment `=`.

5. **Defect D-057 documentation resolution:**
   - Corrected artifact download steps, glob matching (`-p "nextoomio-rpi4-64-*"`), `--dir` extraction directory, uploaded artifact subdirectory layout (`images/raspberrypi4-64/`), distinguishing parse-only vs full-image runs, removing `(16 GiB)` from 16 GB nominal card size, and distinguishing planned update delivery from verified behavior in `docs/bench/first-flash.md`.

6. **Local verification suite:**

## Missed targets

- AC1: Automated CI full-image build on `main` is in progress (run 43832700635, ~2h runtime); artifact publishing on `main` will be completed upon job completion post-merge.
- AC2: Exceeding the 3 GiB root slot size limit was not triggered in CI (the built image rootfs size is well within the 3 GiB partition budget).
- AC3: Comparing layer revisions across two independently completed CI full image runs is pending completed full runs on `main`.
- AC4: The configured gate uses Yocto's `INCOMPATIBLE_LICENSE` to reject AGPL licenses (`AGPL-3.0-only`, `AGPL-3.0-or-later`, `AGPL-1.0-only`, `AGPL-1.0-or-later`) and requires explicit acceptance for flagged licenses via `LICENSE_FLAGS_ACCEPTED`. A full license allow-list rejecting any recipe license outside an accepted set (such as `CLOSED` or unlisted non-commercial licenses, as described in AC4 and ARCHITECTURE.md section 11, item 9) is not provided by Yocto's `INCOMPATIBLE_LICENSE` mechanism alone; defining the accepted license set and deciding whether to implement an allow-list check for the OS image has been filed as finding #246 for the Architect.
- AC4: Intentional build failure by injecting an AGPL recipe into the image build was not run in CI (verified via static layer check in `check_yocto_layer.py` and BitBake configuration).
- No physical bench testing was performed; this enabler story concerns Yocto image build workflow and configuration in CI.
